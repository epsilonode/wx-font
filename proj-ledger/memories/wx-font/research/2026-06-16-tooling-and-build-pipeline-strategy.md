# Tooling And Build Pipeline Strategy

Fantasticon is the preferred compiler because it supports explicit codepoints, TTF/WOFF2, CSS, JSON, TS, and templates.

Use Fantasticon primarily for SVG-to-font binaries and codepoint artifacts. Do not let Fantasticon templates own the complex public WMO CSS contract.

SVGO remains the vector optimization stage before font compilation.

Bun should orchestrate registry validation, SVG staging, Fantasticon execution, generated docs, and preview output.

Generate public CSS layers from registry/mapping contracts with `css-tree` so readable audit output can preserve source/provenance intent before production minification.

Run generated production CSS through Lightning CSS for transform/minification and source maps where useful. Expect Lightning CSS to strip normal comments, so durable provenance belongs in registry data, audit artifacts, readable CSS, and docs rather than only minified CSS comments.

Use `opentype.js` or `fontkit` for post-generation font audits when codepoint-to-glyph mapping, name tables, or metrics need verification. Consider Python `fonttools`/`pyftsubset` only when deeper subsetting or Unicode-range auditing justifies the extra runtime.

Svelte/Vite tooling is for preview/docs and package ergonomics. Library CSS classes are public API, so do not use CSS Modules or Svelte scoping for generated package CSS.

Custom CSS templates may still be useful for Fantasticon smoke tests, but production `.wx-*`, `.wi-*`, `wx-wmo-*`, color, and description CSS should be generated by the registry-driven CSS pipeline.

Keep Fantasticon as an implementation tool, not the source of truth; registry and codepoints manifest own intent.

Open proof: verify Bun plus Fantasticon fixed codepoints, css-tree CSS generation, Lightning CSS output, and font audit tooling with a small deterministic smoke build.
